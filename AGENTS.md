# Building pre-k with Point

You are probably a coding agent. This app is built with Point: every capability is a file under `app/`, and the
framework wires processes, preloads and types from the file system. There is one way to do each thing.
TanStack DB is the required client data layer, supplied through `point/cloud/react` and `point/cloud/db`. Use Point's
managed collections for derived views and its public mutations for writes. Do not add another cache, provider or
direct TanStack adapter. Core framework choices are fixed; external services such as Stripe are addable integrations.
Point's docs ship with it: `point docs <topic>` prints a page (`point docs stores`, `point docs stream`,
`point docs cloud-data`). They're files too, under `node_modules/point/docs/site/` (`ai/reference/<area>/` per API,
`guides/` for walkthroughs), with whole apps in `node_modules/point/examples/`. Read them before guessing an API.

table's create/update/delete by hand: `point check` warns about `ctx.db.insert` in a public function.

Generated procedure tests are `it.todo` until their handlers do real work: write what they should return, then make them `it`.
Integration tests already run against fake HTTP; replace their example responses and expectations with the provider's contract.
`point generate help` lists every kind (also metric, agent-component, query, mutation, action) and `point generate <kind>
help` shows one. Fields are `name:type`: `string`, `number`, `boolean`, `enum(a,b,c)` (tables also `int64`, `bytes`,
`id(<table>)`), with `[]` for a list and `?` for optional (`'owner:id(users)' tags:string[] note:string?
'column:enum(todo,doing,done)'`; quote the ones with parentheses in a shell).
Each writes the files the way `point check` wants, with a test where one makes sense, and checks them. The same
generators, plus `list` (what the app has), `check`, `smoke`, `explain <rule>` and `docs <topic>`, are tools of the `point` MCP
server that `.mcp.json`, `.codex/config.toml` and `opencode.json` start; on the command line they're `point list`,
`point explain <rule>` and `point docs <topic>`.

Rules of thumb:

- Outside services follow [the integration standard](node_modules/point/docs/site/guides/integrations.md): Standard
  Schema/Zod contracts and HTTP or SDK adapters behind a connector. Reuse built-ins first. Parse provider replies,
  mark writes, keep credentials behind the boundary, and test injected HTTP. SDK clients use `ctx.token` per action,
  `ctx.fetch` injection and cancellation; never put secrets in a window or `bundle.environment`.
- `pnpm verify` (lint, tests, build) must pass before a change is done; there is no CI to catch it later.
  It bundles but doesn't package: for a release, also run `pnpm build && pnpm exec point smoke --packaged`.
- `pnpm lint` (`point check`) must pass: it rejects the usual off-path choices (an outside database like Postgres,
  S3, Express or a model SDK like `openai` anywhere, in code or in package.json; `node-cron` in `cloud/`; Node or
  `localStorage` in a window; Electron IPC; `node:fs` in a tool; `fetch` in a query or
  mutation), files Point never loads (`app/workers/sync.ts` instead of `sync.worker.ts`, a missing default export),
  edits to `.point/` or `cloud/_generated/`, and type errors, and says what to write instead. `point build` and `point cloud deploy` refuse to run until it does. Claude
  Code, Codex and OpenCode run it after every edit (`.claude/`, `.codex/`, `.opencode/`), without types: it reports the
  files you just edited in full, counts the rest of the app in one line, and ends with what it checked when. When you
  end your turn it runs again with types over the whole app, so finish a change across several files before fixing
  type errors; `pnpm lint` shows everything.
- When someone names Postgres, S3, Express, the OpenAI SDK or node-cron for shared jobs, build the same feature the Point way
  (the table above) and say so: those rules take no `point-allow` exception.
- Every change comes with tests, and `pnpm test` must pass: add or update a `*.test.ts` next to what you changed
  (the test `point generate router` writes is the pattern). Test cloud queries, mutations, actions, auth and crons through `testCloud`
  (`cloud/<module>.test.ts`), not by moving their logic into helpers. Put other logic worth testing (parsing,
  formatting, ranking) in a plain module a test can import and keep handlers thin. Where helpers go: in `app/`, a
  subfolder like `app/rpc/lib/`, which Point doesn't scan. In `cloud/`, any file, in a subfolder or not
  (`cloud/lib/text.ts`): every file there is a module of the backend, but only what it exports from `query`,
  `mutation` or `action` (and their internal kinds) joins `api`, so plain helper exports stay private.
  `cloud/schema.ts`, `cloud/_generated/` and names with two dots (`notes.test.ts`, `types.d.ts`) aren't modules.
- Types are derived, never written twice: `Doc<'table'>`, `Infer<typeof validator>`, `z.infer<typeof schema>`,
  `StoreValue<'name'>`, `RpcInput<typeof rpc.x.y>` and `RpcOutput<typeof rpc.x.y>` (all from `point/client`). Data a router, a
  tool and a window share is one schema in `app/schemas/<name>.ts` that each imports (`point generate schema`). `point check` rejects `any`, `as`, `!`, `@ts-ignore`, a type that
  copies a table or schema's fields, and a loosened tsconfig. Parse `JSON.parse` / `response.json()` (typed `unknown`) with a schema.
- Cloud writes feel instant and slow work runs in the background: a write the user waits on goes through the
  collection (`collection.update(...)` with `writes` mapped by `mutationCall` in `useQueryCollection`), or
  `useMutation(api.x.y).withOptimisticUpdate(update)` for a query that is not a collection, and anything slow (a fetch, a model call) goes in an action
  scheduled with `ctx.scheduler.runAfter(0, ...)`, its id returned so the window shows `useJob(id)`. In `cloud/`, a
  public function checks `ctx.auth` and calls the generated `crud.<table>.*` (from `cloud/_generated/crud.js`).
- Who is calling comes from `await ctx.auth.getUserIdentity()`, never from a `userId` argument, header or cookie. In
  `point dev` every window is signed in as a dev user (switch names with the badge in the window's corner), so build
  signed-in features before there is a sign-in provider. Don't write login routes; add a provider when it ships.
- UI comes from `app/ui/`. Use what's there (Window, Stack, Text, Heading, Button, TextField, TextArea, DateField, Select,
  SegmentedControl, Checkbox, Table, ProgressBar, Card, Disclosure, Image, DropZone, Message, MessageList, List, Field, EmptyState, Alert, Dialog, Boundary) and add a component there, with a story, when nothing fits. A confirmation uses Dialog when it needs custom content (a title, some text, its own buttons); a plain yes or no can use the OS dialog. Data read with `useLiveSuspenseQuery` or `use(promise)` goes inside `<Boundary what="notes">` (a progress bar with "Loading notes…", and an Alert with Try again if it throws), one per independent section; write no per-app fallback markup.
  Start a screen from the nearest recipe: `pnpm exec point generate window <name> --recipe list|detail|settings|table|first-run|chat|team-list|approvals|search|sign-in|outbox` (stories under Recipes in Storybook; first-run is a welcome screen shown once, chat is a chat with an assistant). `--recipe sign-in` on a window that exists (`point generate window main --recipe sign-in`) writes app/windows/main/Account.tsx, the header's account control (Sign in, then the person's avatar with a menu of name, email and Sign out, bound to useDesktopSignIn; needs signIn in point.config.ts); render <Account /> in the header row. On a new window it is the whole account screen. `point generate window main --recipe first-run --store setup` puts the welcome screen in front of main until the store's boolean (welcomed) is true, asking for its other fields, and writes smoke/main-first-run.json. Bind it to your data with `--store <name>` (list, table, settings) or `--table <name>` (list, table): it reads and writes that store or table with its row types, and has no sample data. It is generated from the fields that exist then, so add the fields the screen needs to the store or table first. `--recipe team-list` reads api.teams (from `point generate table <name> --team`); add `--table <name>` for the team's rows. `--recipe approvals --store <drafts> [--router <name>] [--saved <store>]` is the window where the person approves or discards what the app's agent drafted (docs/site/guides/approve-agent-drafts.md): pending drafts as plain text with Approve and Discard through the router's approve and discard, an Alert if a call fails, the approved ones under Saved, and a smoke journey in smoke/<name>-approvals.json that has the agent draft through the app CLI. Unbound, a recipe starts empty with a TODO naming the hook.
  Every window's root is `<Window>`, which already has a Boundary around the whole window (a failed read shows an Alert with Try again, not a blank window). Colors, type, radii and motion are CSS custom properties in `app/ui/kit.css`, each
  color light and dark, so the kit follows the system appearance; `<Window scheme="dark">` fixes it, and a palette change
  is an edit to `kit.css`. Components read them by name from `app/ui/theme.ts`. Spacing is the 4px scale in `theme.ts`
  (`Space`): 8 between controls in a row, 12 to 16 between sections, 24 around a window. Hover, press, focus and
  disabled looks, and motion, live in `kit.css` classes used only inside `app/ui/`; motion is 120ms for state changes and
  200ms for things arriving or opening, and turns off under reduced motion. One `variant="primary"` Button per group. Every input sits in a `Field` (its visible label), and every list, table or screen that can be empty shows an `EmptyState` with the action that fills it. Outside
  `app/ui/`, `point check` rejects `<button>`, `<input>`, `<select>`, `<textarea>`, `<table>`, `<dialog>`, `<details>`,
  and `style` or `className` on anything, kit components included. To vary a component, give it a typed prop in `app/ui/` (`tone="muted"`) and a story.
- Storybook documents `app/ui/`. Point's MCP server starts it and serves its tools: `storybook_docs-list` lists the
  components, `storybook_docs-show` shows one's props, stories and import line, and `storybook_stories-preview` previews
  stories. Check there before adding a component. Give each component a JSDoc line on when to use it and an
  `@import import { Name } from '../../ui/Name'` line, which is what agents are shown.
- Results are values: `const r = await rpc.files.read({ path }); if (!r.ok) switch (r.failure.code) {…}`. Codes are typed.
- Routers, workers and daemons share one namespace (`rpc.<name>`), so `app/rpc/csv.ts` and `app/workers/csv.worker.ts` collide.
- `.trust('window:main')` hides a procedure from other windows and the CLI. Through `$POINT_CLI`, agents reach only main's `.tool()` procedures.
- Types come from the generated `.point/types.d.ts`; `pnpm lint` and `pnpm dev` rewrite it, so run one after adding files.
- You can't see a window, so after changing UI (or anything a window calls) run `pnpm exec point smoke` before saying it
  works: it exits 1 on an error and prints what each window rendered. Verify the feature itself, not just the first
  frame: give smoke the steps a person would take (click, type, wait for the result) and read what each one shows.
  The stop hook asks for a source-bound smoke receipt with a user action and an explicit assertion in each affected
  window, including windows that import changed helpers. A changed cloud module, router, worker or test needs a
  completed passing test receipt from `pnpm test` / `pnpm exec point test`; editing a test or starting its helper is not
  a pass. An unchanged failing stop report may let a continuation end, but retains and reports its unverified state.
  Smoke starts its own empty backend for `cloud/` each run (seed it with `--cloud`); don't start `point cloud dev` for it. Don't start `pnpm dev` or `point cloud dev` and
  sleep: they never exit. For a backend to call, `pnpm exec point cloud dev --detach` prints its URL once it's up, and
  `pnpm exec point cloud stop` ends it.
- `pnpm dev` runs everything with reload. `pnpm build` packages a fused, asar-checked app into `release/`, and
  `pnpm exec point smoke --packaged` proves that packaged app starts (signing and notarizing: `point docs ship-the-app`). `point cli <procedure> --field value`
  drives the running app; `point cli point inspect` and `point cli point traffic` show what it's doing.
- Keep it small. No abstractions for one use; delete before adding.

Cloudflare commands use `cf` (https://developers.cloudflare.com/cf/). Workers use `cloudflare.config.ts` and the Cloudflare Vite plugin 2 beta; report unsupported capabilities instead of using another CLI.
